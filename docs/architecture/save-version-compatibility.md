# 地图存档逐版兼容契约

本程序生成的旧存档是长期用户数据。每次正式版本升级都须能把此前由本程序生成的存档迁移到当前结构，旧字段缺失不能直接归为玩家存档损坏。对确实丢失且无法从存档中恢复的数据，保留原始存档并给出可诊断的失败原因。

## 版本边界

- 地图文档的 `version` 和地图 schema 标记由 `map-file-io.js` 管理。截至 `0.5.141`，文档与地图 schema 均为 `v2`，文档 `v1→v2` 已登记迁移。早期同版 v2 曾逐次添加字段，现有同版回填继续保留，不能删除以往兼容逻辑。
- `.webfmg` 的 `WEBFMG3` 是二进制容器版本，与内部文档和地图 schema 版本分别计数。以后替换容器时须保留旧容器解码器，再把解码出的内部文档送入同一迁移链。
- 浏览器 LocalStorage 包装、IndexedDB 二进制记录也各有版本。它们只负责解包，解包后使用与文件导入相同的文档迁移路径；历史已发行的包装和编码不可因默认写入方式改变而删掉读取能力。

## 新字段和校验升级

新增持久字段、改变既有字段含义、删除旧表示方式或收紧会拒绝旧档的校验时，先定义旧值如何推导、回填或映射，再提高相应文档 / schema 或包装版本，登记单步迁移 `vN→vN+1`。迁移步骤不得跳过历史版本，也不得只更新当前生成器。保持原有用户自填资料和稳定身份；仅在来源字段足以唯一推导时构造派生记录。旧版本中曾合法存在、如今缺失的字段应在迁移中补齐。

地图主体结构升级时同步提高文档 `version` 和地图 `schemaVersion`，在文档迁移注册表中逐版推进并设置新 schema 标记；不能只改 schema 常量而没有对应迁移器。拥有独立版本的子结构应保留自身旧版迁移，并由共同文档导入链调用。

输入顺序固定为：识别本程序格式与外层版本 → 解包 → 按内部文档版本逐步迁移 → 兼容旧地图字段及索引 → 当前版本校验 → 原子提交前台。升级后的保存写当前版本。迁移失败不覆盖浏览器原记录或当前地图；普通界面给简短反馈，技术原因进入调试诊断。外部格式与无法解析的破损数据可拒绝，明确记录原因。

旧档在打开过程中确需逐版迁移或历史回填时，向玩家显示无按钮的整理进度提示；提交成功后再告知整理完成，失败不得显示完成提示。升级不征求同意，也不增加第二次确认。替换当前地图时原有的确认仍用于保护玩家尚未保存的改动。提示所需来源信息只随本次解析结果传递，不写回地图文档或原始存档。

已明确声明高于当前程序的文档、地图 schema 或二进制容器 schema 时，旧程序必须报“未来版本不支持”，不得先把版本标记覆盖成当前值后尝试导入或导出。缺失的历史标记仍按旧版兼容规则回填。

## 回归门

历史夹具必须冻结其旧版本标记与典型缺失字段，不允许在测试运行时用当前 `createMapDocument` 重造旧输入。每次改变保存结构或导入校验，至少验证最早支持版本、上一个已发行版本、浏览器包装、`.webfmg` 容器和真实旧档中的代表性一份；核对迁移后字段、自有资料、原记录保持以及再次保存 / 读取。二进制夹具应由已发行版编码器生成并固定字节及哈希，专项运行时不得重新编码来替代旧版解码覆盖。缺失单步迁移器应明确失败，不能静默跳到当前版本。新增版本时先加入旧版固定夹具，再升级版本常量和迁移注册表。
