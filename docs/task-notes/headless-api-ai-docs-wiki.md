# 第 223～226 项：无头 API、AI 文档系统与 GitHub Wiki 施工图

## 一、背景与目标

当前正式应用已经具备完整地图存档、公开浏览器 API、方法 schema、稳定业务 code、规则 inspector、事务执行和 AI 规划器配方。现有能力适合页面内控制台和自动化回归，但默认 AI 会话仍难以快速完成以下工作：

1. 不依赖浏览器读取一份完整地图存档。
2. 正确理解 Grid、Pack、地形、气候、水文、适居度、人口、政治、经济和军事数据。
3. 按统一口径定义地理区域、聚合数据、比较区域并解释因果。
4. 根据自然语言目标找到正确事实、inspector、事务和派生重建顺序。
5. 在 AI 文档与人类文档中获得细致、完整且不会随 API 漂移的功能说明。

本批目标不是新增聊天框，也不是复制第二套领域逻辑，而是建立浏览器和无头环境共用的地图应用核心、无浏览器 API 运行时、AI 文档系统和 GitHub Wiki。完成后，默认 AI 会话只获得接手入口和地图存档，也能在不启动浏览器的前提下完成可靠的地图诊断。

## 二、统一架构原则

### 2.1 浏览器与无头 API 的关系

浏览器 API 不建立在无头 API 之上，无头 API 也不模拟浏览器。二者是同一 API 门面在不同运行时中的并行实例：

```text
共享领域核心
├─ 地图模型、存档迁移与校验
├─ Objects / Cells 查询
├─ 区域定义、聚合与比较
├─ 领域 inspector
├─ 编辑事务与派生重建
└─ API schema、元数据、业务 code 与 ApiResult

共享 API 门面
└─ createMapApi(runtimeHost)

运行时适配器
├─ BrowserRuntimeHost
└─ HeadlessRuntimeHost

传输层
├─ window.webglGeneratorApi
├─ CLI JSON
└─ 后续本地 MCP / 受控标签页桥
```

地图事实、聚合算法、inspector、事务规则、schema 和错误码必须共用同一实现。DOM、renderer、camera、selection、浏览器存储和下载只允许留在浏览器 host；路径读写、批处理和标准输入输出只允许留在无头 host。

### 2.2 能力 profile

同一方法目录必须标明 `browser / headless / shared` 支持情况。无头环境不支持的方法不得静默消失，也不得用猜测结果降级，应返回稳定的 `runtime_capability_unavailable`，并指出所需运行环境。

浏览器运行时可以是能力超集。无头第一期只读，不要求一次迁移全部公开方法，也不把图层、相机、WebGL、页面 health 或 Canvas 下载伪装成无头能力。

### 2.3 调试信息边界

普通领域 API 默认返回完成领域任务所需的有界结构化事实；运行时诊断通过显式 `debug.*` 读取。浏览器 `debug.enable / disable` 只控制开发模式 UI，不改变普通 API 返回结构、权限或详细度。

无头运行时可提供地图解析、迁移、校验、分析时序和能力 profile 诊断，但必须明确拒绝 debug UI、renderer 和绘制 profiling。

### 2.4 文档单一事实来源

AI 文档与 GitHub Wiki 覆盖同一功能分母，但不人工复制 API 方法 schema。API 目录、方法元数据、错误码、运行时 profile 和配方目录必须从当前 registry 自动生成；人工文档只解释概念、因果、工作流、风险和实例。

## 三、第 223 项：共享 API 核心与无浏览器只读运行时

### 3.1 范围

1. 从现有 `console-api.js` 中识别并下沉与 DOM、renderer 和页面状态无关的共享领域服务。
2. 建立统一 `createMapApi(runtimeHost)` 门面，以及 `BrowserRuntimeHost`、`HeadlessRuntimeHost` 两类适配器。
3. 无头 host 支持读取当前 JSON 与 gzip 完整地图存档，复用现有 typed array reviver、schema 迁移、兼容归一和校验。
4. 第一阶段开放只读和纯预检能力：
   - `info.version / capabilities / describe / mapSummary`；
   - `objects.types / get / list / query`；
   - `cells.get / neighbors / query / scan / actions / inspectAction` 中不依赖 renderer 的部分；
   - `climate`、高度、人口、水文等只读事实；
   - 不写地图的领域 inspector；
   - `planner.listRecipes / getRecipe`；
   - 存档解析、迁移、校验及文本 / GEO 数据导出。
5. 提供 Node API 和 CLI JSON 入口；同一请求与响应使用现有 `ApiResult`、方法 schema、稳定 code 和 JSON 可序列化契约。
6. 第一阶段不离线回写原文件，不实现无头 EditHistory、写事务或派生重建提交。

### 3.2 明确排除

- 不实现 DOM、面板、图层可见性、camera、selection、flash 或 fitView。
- 不实现 WebGL、renderer stats、页面 health 或 `profileNextRender`。
- 不实现浏览器缓存、浏览器下载、原生文件选择器或 Canvas PNG。
- 不建立远程公开 HTTP 服务。
- 不读取浏览器 Cookie、其它标签页或任意 localStorage。
- 不复制一套新的对象查询、Cell 查询、inspector 或存档迁移逻辑。

### 3.3 最小验收

- 同一固定存档在浏览器与无头环境中执行共享只读方法，结果除明确 runtime 字段外结构和关键值一致。
- JSON、gzip、旧版兼容样本和当前地图存档均可无浏览器加载；错误存档返回稳定迁移或校验诊断。
- `info.capabilities` 明确输出 `runtimeProfile`、共享能力、环境专属能力和不可用原因。
- 所有无头调用均可由 CLI 输出纯 JSON；标准输出不混入日志。
- 只读调用前后内存地图 checksum 不变，输入存档文件不被覆盖。
- 浏览器现有 API、UI、存档往返和旧数据兼容回归不退化。

## 四、第 224 项：区域定义、聚合分析与三个真实问题基线

### 4.1 数据理解契约

建立共享数据字典，至少冻结：

- Grid Cell 与 Pack Cell 的职责、ID、邻接和双向映射。
- 高度、海平面、温度、降水、生物群系、适居度、乡村人口和城市人口字段。
- 国家、省份、文化、宗教、城市、路线、河流、资源、市场、经济和军事引用。
- 直接输入、派生字段、手工 override 与 `derivedStale` 的区别。
- 单位、空值、旧图缺字段、typed array 和浮点精度规则。

### 4.2 区域与聚合能力

建立浏览器和无头共用的只读分析命名空间，候选能力包括：

- `analysis.regions.define`：按对象归属、Cell 集合、bbox、多边形、高度带、坡度、连通块和相对方位定义临时区域。
- `analysis.regions.describe`：输出面积、地形、气候、水文、生态、人口、聚落、路线、资源和经济摘要。
- `analysis.regions.compare`：按同一统计口径比较两个或多个区域。
- `analysis.precipitation.explain`：解释风向、水汽来源、迎风坡、雨影和地形屏障。
- `analysis.population.capacity`：区分承载力不足与已有承载力但开发不足。
- `analysis.power.compare`：显式拆分人口、经济、资源、城市、交通和军事贡献，不把人口直接等同国力。
- `analysis.terrain.roughness`：输出邻接高差、局部极差、坡度分位数、异常尖峰、主山脊和潜在水文风险。

统一聚合规则至少包括：面积加权平均、总量、P10 / P50 / P90、连通块、异常值、城乡人口去重和显式国力分项。

### 4.3 三个标准问题

#### 问题一：晴布赫斯王国增雨与增人口

AI 必须能够：

1. 按名称找到晴布赫斯王国并解析其 Cell 范围。
2. 识别西部高山和南部丘陵屏障。
3. 聚合王国内外降水、温度、地形、生物群系、适居度、河流与人口。
4. 解释当前风向、水汽路径和可能雨影，不根据截图主观猜测。
5. 把疆域、海岸、西部主山脊和南部丘陵列为保留约束。
6. 输出气候参数、生态承载和人口调整的候选顺序及全图连带影响，不直接执行。

#### 问题二：高山无人区北侧与南侧平原平衡

AI 必须能够：

1. 识别高山连通块及其北侧、南侧同政权平原。
2. 使用相同口径比较降水、温度、适居度、河流、人口、城市、路线、资源、市场和综合国力。
3. 判断北侧是承载力不足、人口载体缺失，还是基础设施与开发不足。
4. 明确区分增加总人口、人口迁移、新建城市、路线建设和市场接入的不同后果。
5. 在当前人口事务不能处理任意子区域或零人口落点时，返回真实能力缺口，不伪造可执行方案。

#### 问题三：两大陆高山区自然化

AI 必须能够：

1. 识别高山范围、主峰、主山脊、山口、分水岭和区域边界。
2. 输出当前高差、坡度、局部起伏、尖峰和崎岖度统计。
3. 区分大尺度地形关系与小尺度噪声。
4. 说明普通邻接均值平滑可能削弱山脊、山口、雨影和河网的风险。
5. 给出保留主峰、主山脊、海岸和分水岭的约束式平滑建议及后续派生重建清单，不直接执行。

### 4.4 最小验收

- 三个标准问题均使用固定真实地图存档或脱敏固定夹具，在无浏览器环境中完成数据读取、区域识别、聚合和中文诊断。
- 结果包含输入存档 checksum、区域定义、统计口径、关键证据、局限和未执行声明。
- 相同存档和参数返回确定性结果；分页、Cell 顺序和对象数组顺序不改变聚合值。
- 分析前后地图 checksum 和存档文件均不变。

## 五、第 225 项：AI 友好文档系统

### 5.1 单一接手入口

新增 `docs/ai/README.md`，冻结默认 AI 会话启动顺序：

```text
AGENTS.md
→ docs/ai/README.md
→ AI manifest 与 runtime profile
→ 当前地图摘要或无头存档摘要
→ 按用户目标加载领域手册
→ info.describe 读取相关方法契约
→ 先诊断与预检
→ 用户授权后才写入
```

入口必须说明文档权威性顺序、默认只读、安全边界、浏览器 / 无头模式选择、事实 / 规则事务 / 规划器配方三层关系及发生能力缺口时的报告方式。

### 5.2 领域手册

首批至少包含：

- 数据模型与存档读取。
- Grid / Pack、区域定义与聚合统计。
- 气候、降水与雨影诊断。
- 地形修改与派生重建。
- 人口、适居度、聚落和区域开发。
- 国家、省份及对象保护。
- 水文、河流与地形联动。
- 国力比较与指标解释。
- 安全写入、revision、历史、确认和回滚。
- 浏览器运行时与无头运行时差异。
- 调试 API 与开发模式 UI 的区别。

每份领域手册统一包含：用户意图、必读事实、数据解释、聚合口径、因果关系、保留约束、方法调用顺序、inspector、执行方法、副作用、成功条件、失败 code、只读示例、预检示例和写入示例。

### 5.3 机器目录

从 API contract、schema registry、方法元数据、业务 code 和 planner recipe registry 自动生成：

```text
docs/generated/ai/
  manifest.json
  api-catalog.json
  api-catalog.md
  recipe-catalog.json
  domain-capability-map.json
```

机器目录至少记录 API/schema 版本、运行时 profile、方法输入输出、副作用、确认、撤销、异步、inspector 配对、业务 code、领域手册路由和配方步骤。

### 5.4 最小验收

- 当前全部公开方法和规划器配方进入机器目录，声明 / metadata / schema / runtime 双向差集为零。
- 手册引用的每个方法、code 和字段真实存在；失效链接、陈旧版本和未路由方法使门禁失败。
- 默认 AI 会话只读取 `AGENTS.md`、AI 入口和一份地图存档，即可通过无头 API完成三个标准问题的证据化分析。
- AI 不读取内部 map 对象，不把 debug UI 当权限开关，不在未授权时写地图。

## 六、第 226 项：GitHub Wiki 人类文档

### 6.1 发布方式

使用仓库对应的 GitHub Wiki 机制维护人类友好文档。Wiki 与仓库文档使用独立发布流程，但内容来源和版本必须可追踪；不得只依靠网页手工维护而没有可复现源稿或同步检查。

正式实施前需确认 Wiki 是否已启用、对应 `.wiki.git` 远端、发布权限和仓库内源稿放置位置。任何远端创建或推送动作均需按用户当时授权执行。

### 6.2 内容范围

Wiki 需要细致覆盖：

- 项目介绍、安装、启动、地图创建、保存和导入导出。
- 地形、气候、水文、生物群系、人口、政治、文化、宗教、城市、路线、经济、外交和军事系统。
- 全部编辑器、面板、图层、对象详情和典型工作流。
- API 概览、浏览器 / 无头环境差异和自动化使用方式。
- 数据字段的人类解释、单位、派生关系和常见误区。
- 三个标准问题的完整教程。
- 安全修改、锁定、历史、回滚、旧图兼容和故障排查。

Wiki 与 AI 文档覆盖同一能力分母，但表述面向人类：增加导航、截图、操作步骤、概念解释和常见问题；不复制机器 schema 大表。

### 6.3 一致性与最小验收

- 建立“能力 → AI 手册 → Wiki 页面”覆盖矩阵，所有公开功能均有归属，缺口为零。
- API、配方或功能发生变化时，生成门禁能指出受影响的 AI 手册和 Wiki 页面。
- GitHub Wiki 首页、侧栏、领域目录、跨页链接和版本标记完整。
- 三个标准问题可以由普通用户按 Wiki 教程理解并复现诊断过程。

## 七、候选后续：受控标签页桥与安全写入

该部分记录依赖方向，不属于前述第一阶段的默认实施范围。

1. 本地、显式启用的受控桥连接当前打开的地图标签页。
2. 默认只读，方法白名单可发现；不读取其它标签、Cookie 或任意 localStorage。
3. 写方法要求用户授权、当前地图 identity、expectedRevision、inspectionToken 和 API 自身确认策略。
4. 所有调用记录 `requestId / method / code / revision / affected`，不记录整份私有地图。
5. 后续无头写入必须提供独立 HeadlessHistory、事务回滚、派生重建和“输出新文件、不覆盖输入文件”的硬边界。

## 八、统一执行顺序

已批准的封闭依赖顺序为：

1. 共享 API 核心与无浏览器只读运行时。
2. 区域定义、聚合分析与三个真实问题基线。

每项达到最小验收后立即转向下一项，不把后续写入、聊天 UI、远程 HTTP、局部气候覆写或地貌算法改造提前塞入当前项。
