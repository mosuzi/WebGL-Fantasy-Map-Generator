# 第 416 项：线上启动脚本状态与冷启动响应

## 现场根因

线上 `0.5.136` 的启动页在固定三秒后，仅因 `window.__webglGeneratorApp` 尚未出现就进入不可逆的 `error` 状态。隔离 Chrome 在 `180 KiB/s` 下载条件下观测到：文档启动 `37894.9ms`、误报 `40895.8ms`、应用实际就绪 `44251ms`；网络请求和模块执行均无错误。应用随后生成地图，但加载页的完成函数拒绝关闭已经标记为错误的遮罩，因此玩家永久看到“脚本尚未启动”。

## 修复

- 三秒仍未出现应用对象时保持加载态，并写入非终态的延迟诊断；只有真实模块资源或执行失败才显示错误。
- 入口模块和按需导入的应用模块分别捕获加载与执行异常，记录原因，并给出适合网络失败或执行失败的中文提示；刷新后允许恢复。
- 大型运行时在独立任务导入；控制面板七页逐页挂载、全部就绪后再绑定旧 DOM 控件；WebGL 程序、城市图标、数值图层等资源逐阶段创建。启动期间如 WebGL 上下文丢失，按上下文代际清理部分资源，等待恢复后重建；地图就绪后的恢复路径保持原有事务。

## 本地验收

- `0.5.137` 正式构建的隔离 Chrome 覆盖普通冷启、同页热重载、入口延迟 `5.5s`、入口断网与执行异常、按需应用模块断网与执行异常、网络恢复刷新，以及首次 `createProgram` 内注入的 `lost → restored`。普通冷启 LongTask 最大 `160ms`，热重载 `104ms`、延迟入口 `125ms`，所有场景原始最大 `160ms`，严格小于 `200ms`。延迟场景在 `3.3s` 仍为加载态，恢复后地图就绪；应用模块断网与执行异常提示准确，上下文重建后的地图和资源状态为 `ready`。完整本地结果见 `docs/generated/task-416-startup/result.json`，逐次失败归因见同目录 `retries.md`。
