# 第 496 项评审方案：全项目状态管理与 Canvas 差分更新

**独立分支已验收，版本 `0.7.3`。** 基线为包含第 480 项的主线 `87bd15e`（`0.7.0`），独立分支 `codex/496-reactive-map-state`。原问题在 `0.6.29` 复现。

总目标覆盖整个正式应用。每类可变状态需要明确所有者、写入入口、消费者、失效条件和生命周期。文化改名是第一条跨面板验证链，海岸平滑是第一条高负载 Canvas 验证链。两条通过后继续迁移各领域并清理旧同步路径，整体验收通过才关闭本任务。

## 已查明的问题

1. 文化管理从 `society.cultures` 读文化。手动改名事务修改优先找到的那份记录，`society` 与 `pack` 都存在且各自独立时，只改了前者。名称库的文化选项优先从 `pack.cultures` 读，也没有过滤已删除文化。这会让重新打开面板仍显示旧名。
2. 名称库的 `panelState` 是浅响应式。文化选项的 `computed` 只读取 `state.map`，原地改名时地图引用保持，现有面板刷新即使重新设置该引用也不会让这个计算值失效。面板目前还有一个较粗的 `version` 用于词库列表。文化选项和词库统计需要各自的依赖，不宜用同一个刷新计数器。
3. 现有 `EditHistory` 统一记录执行、撤销、重做。主线程维护地图身份、修订和历史，Worker 已有字段、对象行、区段补丁与校验。当前 `MapRevisionTracker.advance()` 对任一编辑都推进全局拓扑修订。部分 Worker 流程在渲染安装成功前已执行历史命令，失败时再回滚。订阅通知需要在最终成功处发布，`onMutation` 只适合先收集。
4. 现有海岸局部更新可复用未变岸段，部分平滑几何已经在 Worker 准备。岸段身份与路径对象或合并后的数组范围有关，填色更新路径仍可拼接整段缓冲。当大型岸线连通、水域改分类、保护对象变化或性能回退时，实际工作可能超过改动格的邻域。

正式 Chrome 使用 10,004 格旧档复现。先打开名称库，再切到文化管理将「昭宁文化」手动改为「青崖演示文化」，然后重开名称库。两份地图记录和文化列表都显示新名，名称库下拉仍显示旧名。第二轮只在隔离夹具里将这两份记录拆开，首次在改名后打开名称库，此时规范记录为新名，镜像和下拉均为旧名。原始结果在 `Z:/tmp/codex/2026-11-28/fmg-reactive-map-state/actual.log` 和 `separate.log`。未测修复后的延迟和海岸性能。首次旧档导入超时，加入默认地图就绪等待后通过。后来面板切换会隐藏文化管理，调整为切换前采样其列表。

## 状态所有权与更新路径

采用统一的读写与订阅契约，各领域各自拥有其状态。规范地图和编辑历史沿用现有地图所有者。选择、会话、设置和任务各有提交入口及作用域。Vue 组件订阅只读的小投影，使用浅响应式引用，原地可变数据通过已提交写集触发更新。网格、邻接、TypedArray、空间索引和 WebGL 资源由相应领域持有。Canvas 只消费实际依赖发生变化的投影。草稿和落笔预览采用独立序列，取消时清理草稿，历史、保存和其他面板读取提交态。

由事务写集驱动发布。用户动作、公开 API、导入、生成、撤销和重做经同一领域提交边界提供结果。通知携带作用域身份、基础与结果修订、变更对象或网格范围，以及写入路径或已验证的失效范围。地图身份用于区分替换和新建，地图修订标记提交顺序，领域拓扑、视图和用户设置各自按实际变化推进版本。复用现有 `map-core-engine`、`domain-manifest-registry`、`dependency-registry` 和 revision / binding 契约，先核对其在正式入口的接入程度。一次跨域编辑按同一提交身份发布，消费者按依赖顺序读取一致的结果。失败和无变化编辑不发布地图变化，操作状态仍可发布明确的结果。订阅者故障时按当前提交重建本投影，换图时以新身份隔离旧任务和旧回调。

规则适用于项目级共享状态。组件内的焦点、弹层开合、表单临时输入由该组件持有，跨组件面板偏好和当前工具由其管理者持有。写入地图数据、共享 UI 或持久化配置时，经其所属领域提交。旧刷新入口可在迁移期兼容，按对应消费者逐项退役，并记录需要整域重算的真实依赖。优先复用现有 Vue 和状态工具。

## 两条端到端验证链

文化使用稳定 ID。由文化事实表派生存续文化的 ID 和显示名，缺主表时按旧档兼容规则补全并校验。不同写法的名称绑定仍以文化 ID 保存。文化管理和名称库使用同一个名称投影，面板筛选、当前选择和未提交草稿继续放在各自局部。规范记录和必要镜像由同一事务写入。文化改名的 `name`、`root` 备份分别记录，撤销/重做能恢复两份记录的准确前后值。词库摘要只在词库或绑定实际变化时计算。

海岸的基础输入是地块身份、共边邻接、地块水陆及水域归属，加上河口、城镇与交通等保护关系。提议建立可从规范地图重建的海岸投影。用同一地图内稳定的边身份保存两侧地块、方向和岸线类型，维护格到边、边到连通路径、保护对象及路线到受影响岸区的索引。海岸开放路径和闭环由这些边导出。编辑时从确实跨越海平面的格子和邻边起算，含湖海连通性变化、合并、拆分、退为硬边及包围盒扩张所涉及的连通部分。变更区域不能仅以画笔外接矩形断定。按实测选择岸段或相连岸组作为计算单元，边界固定端点和描边、水陆修补面的输入一致。第一轮只新增可重建的运行时状态，涉及存档字段变更时另行评审。

## 并发、帧预算与降级

- 同一地图上的历史提交按序保留。绘制可以在一帧内合并连续修订。地图切换、撤销、视图或主题变更、WebGL 上下文恢复都必须校验相关版本。遇到重复、迟到或修订不连续的补丁时丢弃过期结果，从当前已提交版本重算受影响域。
- Worker 收到的岸边或保护对象输入以基础修订核对。地图修订、领域拓扑修订与视图样式修订各自承担不同作用。文化改名应不让岸线投影失效。第一阶段使用订阅和失效域过滤，先不改变旧全局拓扑修订的对外语义。
- 显示使用一套已提交的画布投影。准备期间保留上次完整画面并继续接受输入。最终一次切换受影响的岸面、描边和依赖投影；拾取按当前可见版本解析。若使用待更新预览，预览不得混入正式拾取或导出。保存使用已提交地图事实，导出图像等待同一版本的画布投影。
- `requestAnimationFrame` 用于合帧与提交，重计算移到 Worker。主线程只做版本校验、受控上传和提交。建议初始主线程准备预算为每帧 4 ms，按真实数据验证后再定，驱动调用大小按字节和实测约束。界面交互取同一地图、浏览器、视图和笔划做前后比较，记录 P50/P95、帧间隔、LongTask、统计/几何/上传/提交各段耗时。新增普通局部画笔链以无 ≥50 ms 长任务为目标，有 >200 ms 长任务为硬阻断。大范围连通性变化按实际影响扩大计算，并记录原因。若证据表明瓶颈仍在 WebGL 提交，再提 Canvas 线程迁移方案评审。
- 第 480 项的已交付代码已进入基线。海岸阶段共用现有局部高度编辑契约。

### F 阶段终验记录

- 正式分支构建、709 个排版状态、界面文案、类型检查、选择与工具、后台操作、名称库、海路局部性及 100k 洋流全域依赖链通过。洋流链覆盖各段注入失败、取消、过期、单历史、编辑资料和多格式回读。
- 旧档回归首轮发现最长任务 213 ms。隔离分支复验为 229 ms，落在准备阶段。主线 `0.7.0` 同档对照中，重启恢复的标签绘制阶段最长 242 ms。CPU 采样将分支导入和恢复内的 203 / 232 ms 长任务定位到可编辑地图的深层数组转换。待安装地图的转换改为按四毫秒预算推进，沿用完整迁移链和对象身份，保留同步入口供 Worker 及局部补丁使用。分片后恢复仍有 212 ms 落在标签呈现附近，将国土内标签预排移入既有分批准备。此后最长任务降至 192 ms，但恢复墙钟 7,037 ms 超过 7,000 ms 门槛。遍历改为迭代推进，最终同一旧档导入 / 重启恢复为 4,506 / 6,176 ms，最长任务 107 / 174 ms。时延值来自一次完整正式复验。
